# Запуск на VPS через Docker

Это подготовка к публикации. Сайт пока не опубликован. На текущем компьютере Docker отсутствует: контейнер, Linux-зависимости и выпуск HTTPS-сертификата ещё не проверены на VPS.

## Что потребуется

Один Linux VPS с Docker Engine и Compose v2, постоянным диском и доступом по SSH. Запускать один экземпляр приложения: SQLite и фотографии находятся в общем томе shop_data. Для публикации потребуется домен с DNS-записью на VPS и открытые порты 80/443. Учётные данные хостинга и секреты сохраняйте на сервере, не в чат.

Образ использует Node.js 22 и непривилегированного пользователя node. База, фотографии и резервные копии лежат вне исходного кода. .dockerignore исключает локальные ключи, базу, временные пароли и тестовые данные из контекста сборки. CLI-зависимости сохранены в контейнере для сверки платежей, писем и резервного копирования. Перед размещением обновите базовые образы; инструкции основаны на официальной документации Docker: https://docs.docker.com/guides/nextjs/.

## Подготовка файлов

Скопируйте исходники на VPS без node_modules, .next, .qa, .env.local и data. В папке проекта:

```sh
cp deploy/environment.example .env.production
chmod 600 .env.production
```

Сначала оставьте PAYMENT_MODE=demo и EMAIL_MODE=disabled. ADMIN_PASSWORD_HASH можно оставить пустым для создания нового аккаунта. Файл .env.production исключён из Git и Docker-контекста. Не используйте в этой конфигурации ключи рабочего магазина.

## Закрытый запуск и проверка контейнера

```sh
docker compose --env-file .env.production build shop
docker compose --env-file .env.production up -d shop
docker compose --env-file .env.production ps
docker compose --env-file .env.production logs --tail=100 shop
```

Без профиля public доступ открыт только на 127.0.0.1 VPS. Для проверки со своего компьютера создайте SSH-туннель: ssh -L 3000:127.0.0.1:3000 пользователь@сервер. Освободите локальный порт 3000 и откройте http://127.0.0.1:3000. Проверьте каталог, сохранение фото, заказ, демооплату и сохранение данных после docker compose restart shop.

Если база новая и ADMIN_PASSWORD_HASH пустой:

```sh
docker compose --env-file .env.production exec shop npm run admin:setup
mkdir -p "$HOME/shop-secrets"
chmod 700 "$HOME/shop-secrets"
docker compose --env-file .env.production cp shop:/app/.qa/admin-access.txt "$HOME/shop-secrets/admin-access.txt"
chmod 600 "$HOME/shop-secrets/admin-access.txt"
```

Прочитайте пароль на сервере, войдите в /admin, смените пароль во вкладке «Доступ», затем удалите временный файл. Дальше пароль хранится в базе и сохраняется при замене контейнера. Пересоздание аккаунта не требуется.

## Перенос существующих товаров и заказов

На локальном компьютере выполните npm run backup. Полученную папку shop.sqlite + uploads перенесите по SSH в закрытую папку VPS. Это также переносит актуальный пароль администратора, товары и заказы. Для импорта существующей базы сначала остановите shop, сохраните резервную копию данных назначения и скопируйте файлы в том через временный контейнер с этим же volume. После копирования назначьте владельцем UID/GID 1000:1000. Не заменяйте SQLite во время работы приложения и не переносите только исходный .sqlite без корректного backup: активные данные могут находиться в WAL. Перед импортом обязательно проверьте фактическое имя тома командой docker volume ls; Compose добавляет к нему имя проекта.

## HTTPS — после отдельного решения о публикации

Настройте DNS, затем в .env.production задайте SITE_DOMAIN=ваш-домен и APP_URL=https://ваш-домен. APP_URL должен точно совпадать с адресом в браузере: от него зависят проверка Origin и Secure-cookie.

```sh
docker compose --env-file .env.production --profile public up -d
```

Caddy получает и обновляет сертификат; его состояние хранится в отдельных томах. Приложение остаётся доступно снаружи через reverse proxy. Смена APP_URL требует пересоздания shop этой командой. На публичном домене проверьте каталог, вход, фото, оформление и защищённый доступ к заказу. Прямой внешний доступ к порту 3000 не нужен.

## Тестовая ЮKassa и почта

После проверки деморежима задайте PAYMENT_MODE=yookassa_test, тестовые YOOKASSA_SHOP_ID и YOOKASSA_SECRET_KEY. Для писем задайте EMAIL_MODE=resend, RESEND_API_KEY и EMAIL_FROM; отправитель должен быть разрешён в аккаунте Resend. Затем пересоздайте контейнер.

В тестовом магазине ЮKassa настройте HTTPS URL https://ваш-домен/api/payments/yookassa/webhook для payment.succeeded, payment.canceled и payment.waiting_for_capture. Сервер перепроверяет платёж через API. Проверьте реальную доставку уведомления, повтор уведомления, успех и отказ тестовой карты, повтор оплаты и получение письма. Подробности — payments.md и email.md. Открытие страницы успеха не подтверждает оплату.

Периодическая сверка и обработка очереди:

```sh
docker compose --env-file .env.production exec -T shop npm run payments:sync
docker compose --env-file .env.production exec -T shop npm run mail:flush
```

Добавьте эти команды в cron VPS раз в минуту, используя абсолютную папку проекта и flock для предотвращения перекрытия запусков. Не создавайте второй независимый контейнер с отдельной базой. Реальные списания остаются заблокированы.

## Резервное копирование и обновление

```sh
docker compose --env-file .env.production exec -T shop npm run backup
```

Скрипт использует SQLite backup API, затем копирует неизменяемые фотографии и сохраняет manifest.json. Копии находятся в /data/backups. Скопируйте завершённую папку на отдельный диск/сервер: копия на том же VPS не защищает от потери диска. Автоматического удаления копий нет, настройте срок хранения после оценки объёма.

Для восстановления остановите приложение и восстановите shop.sqlite и uploads из одной завершённой копии в постоянный том, с владельцем UID/GID 1000:1000. Не смешивайте файл базы с WAL/SHM от другой версии. Запустите приложение и проверьте товары, фотографии, вход и статусы заказов. Секреты сервисов восстанавливаются отдельно из защищённого .env.production.

Перед обновлением сделайте backup и сохраните тег предыдущего образа. Затем docker compose build shop и docker compose up -d shop. Том сохраняется. Для отката к старому приложению используйте сохранённый образ; обратная совместимость схемы базы должна быть проверена до отката.

Не применяйте docker compose down -v к нужным данным: флаг -v удаляет постоянные тома.

## Статус проверок

Локально проверяются Next.js-сборка, автоматические тесты, админка и покупательский путь. Резервное копирование проверяется на отдельной базе с восстановлением. Проверка Docker build/up, native-модулей под Linux, HTTPS, cron и внешнего webhook требует VPS или установленного Docker. До этой проверки контейнерный запуск не считается завершённым.
