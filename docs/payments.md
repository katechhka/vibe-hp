# Тестовая ЮKassa — этап 5

Реализован серверный адаптер API v3. Реальные списания запрещены: приложение принимает только PAYMENT_MODE=demo или yookassa_test, ключ с префиксом test_ и ответы с test=true. В .env.example по умолчанию локальный деморежим. В текущем .env.local после проверки пользовательских тестовых ключей включён yookassa_test; локальный режим можно вернуть значением demo.

## Подключение

1. Зарегистрироваться в кабинете ЮKassa и создать **тестовый магазин**. По официальной документации он доступен до заполнения данных компании и заключения договора.
2. В «Интеграция → Ключи API» получить shopId и секретный ключ тестового магазина.
3. Добавить в .env.local, не отправляя секреты в чат и не коммитя файл:

```dotenv
PAYMENT_MODE=yookassa_test
YOOKASSA_SHOP_ID=идентификатор_тестового_магазина
YOOKASSA_SECRET_KEY=test_секрет_тестового_магазина
APP_URL=http://127.0.0.1:3000
DATABASE_PATH=./data/shop.sqlite
```

Сохраните существующие EMAIL_MODE, RESEND_API_KEY и EMAIL_FROM. После изменения режима перезапустите сервер. API-ключи остаются только на сервере.

4. Оформить заказ. Сначала открывается сохранённый заказ, затем кнопка «К тестовой оплате в ЮKassa» ведёт на защищённую страницу провайдера.
5. Использовать только тестовые карты из официальной документации. Например, для успеха Visa 4111 1111 1111 1111; срок действия в будущем, CVC — любые три цифры. Настоящие карты нельзя использовать. Для отказов возьмите соответствующую карту из актуального раздела «Неуспешные сценарии».
6. После возврата на страницу заказа сервер проверяет фактический статус API. Возврат и параметры URL ничего не подтверждают.

На локальном адресе доступны создание платежа и проверка статуса через API. Проверьте, что страница провайдера принимает локальный return_url в настройках вашего магазина. Уведомления требуют публичного HTTPS-адреса — публикация в этот этап не входит.

## Уведомления

После отдельного согласования публикации настройте в тестовом магазине:

- адрес: https://ваш-домен/api/payments/yookassa/webhook;
- события: payment.succeeded, payment.canceled, payment.waiting_for_capture;
- APP_URL на том же HTTPS-домене.

Обработчик ограничивает размер JSON, принимает только известные события и сверяет платёж через авторизованный GET API ЮKassa. Сумма, RUB, test=true, идентификатор магазина, заказа и попытки должны совпасть. Статус и суммы из входящего JSON не используются. Это соответствует документированному способу проверки подлинности через актуальный статус объекта. Заголовок X-Forwarded-For не считается доказательством происхождения запроса.

Неизвестные платежи не изменяют заказы; ответ не раскрывает их содержимое. Повтор успешного уведомления не списывает остатки и не создаёт второе письмо. При временной ошибке проверки возвращается неуспешный HTTP-код для повторной доставки провайдером.

## Хранение и восстановление

Заказ, сумма, доставка и снимок позиций сохраняются до внешнего запроса. Режим зафиксирован у заказа и не меняется при переключении .env. Параметры создания платежа, первый момент запроса и ключ идемпотентности сохраняются в SQLite. Ключ — UUID попытки. Повтор с потерянным ответом использует тот же запрос; подтверждённая отмена позволяет создать новую попытку у того же заказа.

ЮKassa обеспечивает идемпотентность 24 часа. Для неопределённого платежа без сохранённого provider_id после 23 часов автоматическое повторное создание блокируется: требуется ручная сверка в кабинете разработчиком. Резерв сохраняется, чтобы исключить второй платёж и продажу сверх остатка.

Резерв внешнего платежа не снимается локальным таймером. Он освобождается после подтверждённой отмены или списывается один раз после успеха. Если покупатель закрыл браузер и webhook ещё не подключён, запустите:

```sh
npm run payments:sync
npm run mail:flush
```

Для будущего сервера эти команды можно вызывать планировщиком. Планировщик сейчас не настроен. Команда сверяет до 50 ожидающих тестовых заказов за запуск; контакты в вывод не попадают.

Письмо через Resend ставится в существующую постоянную очередь только после подтверждённой оплаты. Это уведомление о демозаказе, не фискальный чек.

## Проверки и границы готовности

- Локальный деморежим сохраняется и проверяется отдельно.
- Автоматические проверки адаптера используют замену API, без обращений в ЮKassa и без отправки писем.
- `npm run build && npm run test:payments` проверяет интерфейс, реальные маршруты приложения и SQLite с тестовой заменой API в отдельном процессе на порту 3004. Подмена не импортируется приложением и включается только тестовым runner.
- Пройденный тест с подменой API **не означает** пройденную оплату в тестовом магазине ЮKassa.
- Тестовые ключи подключены. Проверены создание платежа в настоящем тестовом магазине, защищённая страница, официальный Visa-тест, успешный возврат и подтверждение API. Проверка отказа карты и повторной оплаты описана в payment-live-check-results.json. Для проверки доставки уведомлений всё ещё нужен публичный HTTPS-адрес.
- Рабочий режим не реализован и запрещён. Для настоящего магазина нужны отдельное согласование, оформление продавца/договора, проверка прав на ассортимент, юридические документы, чеки и согласованный процесс доставки/возвратов. Просто заменить test_ на live_ нельзя.
